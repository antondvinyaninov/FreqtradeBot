# История проекта

Этот файл — журнал ключевых решений, развёртываний и проверок. Новые записи добавляются сверху.

## 2026-07-25 — развёрнут и проверен изолированный `freqtrade-research`

### Фактическая конфигурация Easypanel

- В существующем проекте Easypanel `n8n` развёрнут отдельный App `freqtrade-research` из GitHub-ветки `stable`, commit `2ef5618fdf33787b95e0561dde19f1e44ba3e198`, через `Dockerfile.research`.
- Research App не заменяет и не связывает жизненный цикл с рабочим `freqtradebot`: у него отдельные image, deployment и volume. После всех проверок `freqtradebot`, `market-data-collector` и PostgreSQL оставались в состоянии `running`.
- У App нет домена, настроенных или обнаруженных публичных портов и биржевых API-ключей. Auto Deploy оставлен выключенным; replica — одна, start command и entrypoint override отсутствуют.
- В окружении App заданы только `RESEARCH_RUN_ON_START`, `RESEARCH_GIT_REVISION` и секрет `FREQTRADE__DB_URL`. Значение `RESEARCH_RUN_ON_START=0` подтверждено косвенно повторными restart: новый backtest автоматически не запускался, PID 1 оставался `sleep infinity`.
- Подключён отдельный Docker volume `research-data` в `/research`. В контейнере созданы `/research/data`, `/research/results`, `/research/models`, `/research/logs` и `/research/user_data`.
- Контейнер работает как непривилегированный `ftuser` (`uid=1000`), беспарольная эскалация через `sudo` недоступна; image — `easypanel/n8n/freqtrade-research:latest`, публичные порты отсутствуют.

### Read-only PostgreSQL

- Создана отдельная login-роль `freqtrade_research`. Она не является superuser, не может создавать роли или базы, не имеет `BYPASSRLS`, `CREATE`, `INSERT`, `UPDATE`, `DELETE`, доступа к sequences или `TEMPORARY`.
- Роль имеет только необходимые `CONNECT`, `USAGE` схемы `public` и `SELECT` таблиц; для будущих таблиц установлен default grant `SELECT`. На уровне роли задано `default_transaction_read_only=on`.
- Чтобы исключить эффективное право `TEMPORARY`, у базы отозван стандартный grant `TEMPORARY` для `PUBLIC` и явно сохранён владельцу `freqtrade`. После изменения подтверждено: владелец сохранил право, `freqtrade_research` его не имеет.
- Из research-контейнера проверено реальное подключение под `freqtrade_research`: `read_only=on`, `SELECT=true`, `INSERT=false`; контрольный запрос прочитал 659 651 свечу. Строка подключения хранится только как секрет Easypanel и в репозиторий не добавлена.

### Первый серверный baseline и постоянство артефактов

- Вручную выполнен baseline `TrainingStrategy` в Freqtrade `2026.6` на 10 Binance Spot-парах, комиссии 0,1% на сторону, `max_open_trades=1`. Экспортировано 523 651 свеча `5m`; общий диапазон данных — с `2026-01-24 00:30 UTC` по `2026-07-24 20:10 UTC`.
- Получено 1108 сделок: 298 прибыльных и 810 убыточных, итог `-268,33 USDT` (`-26,83%`), profit factor `0,4688`, максимальная просадка счёта `26,83%`. Результат подтверждает прежний вывод: фиксированный baseline убыточен и не допускается к реальным средствам.
- Run `20260724T201227Z` завершился со статусом `success`. В `/research/results` сохранены manifest с revision и SHA-256, ZIP backtest-результата и meta-файл; в `/research/data/binance` сохранены 10 Feather-файлов.
- Постоянство volume проверено дважды заменой контейнера. Сначала контрольный файл сохранился после restart; после baseline SHA-256 всех Feather-файлов, manifest и файлов результата полностью совпали до и после следующего restart. Число run-каталогов осталось равным одному, то есть restart не запустил baseline повторно.
- После финального restart повторно подтверждены `ftuser`, PID 1 `sleep infinity`, mount `/research`, read-only-подключение к БД и состояние `running` всех рабочих сервисов.

## 2026-07-24 — аудит данных, первый baseline-бэктест и план серверного research-контура

### Аудит данных и работающего dry-run

- PostgreSQL проверен напрямую в транзакциях `READ ONLY`: Binance `5m` содержал около 521 тыс. свечей за 180 дней, BingX `5m` — около 133 тыс. свечей за 46 дней, по 10 USDT-пар на каждой бирже.
- Для фактических диапазонов подтверждены 100% покрытие 5-минутной сетки, отсутствие пропусков, дубликатов и timestamps вне сетки.
- Установлено, что Binance и значительная часть funding, open interest и sentiment были загружены задним числом. Для будущих ML-моделей обязателен point-in-time контроль; funding/OI/sentiment не включаются в первый OHLCV-baseline.
- Проверены сделки Freqtrade: на момент снимка было 5 simulated-сделок, из них 4 закрытые убыточные и 1 открытая. Такая выборка недостаточна для оценки стратегии.
- Подтверждено, что рабочий бот продолжает работать на BingX Spot только в `dry_run`, с кошельком 1000 USDT, позицией 100 USDT, `max_open_trades = 1` и таймфреймом `5m`.

### Проверка стратегии и API

- `TrainingStrategy` является детерминированной EMA/RSI-стратегией, а не самообучающейся моделью: вход по пересечению EMA20 выше EMA50 при RSI 50–70; выход по обратному пересечению или RSI выше 75; ROI 3%; stoploss 3%.
- FreqAI в действующей конфигурации не активирован. Его наличие в репозитории само по себе не означает, что стратегия обучается.
- В Easypanel настроены серверные переменные Freqtrade REST API, после чего отдельно проверены `ping`, авторизация, `status`, `profit` и `show_config` — все запросы вернули HTTP 200.
- После изменения API подтверждено, что бот остался в состоянии `running`, использует BingX, `TrainingStrategy` и режим `dry_run`.
- Параметры API сохранены вне репозитория в `~/.hermes/.env` с правами `600`; секреты в проект не добавлялись. Ранее раскрытые в переписке пароли и строки подключения подлежат ротации.

### Первый корректный Binance-бэктест

- Создан `scripts/export_market_candles.py`: он читает `market_candles` через отдельную `READ ONLY`-транзакцию, проверяет сортировку, уникальность timestamps, 5-минутную сетку и OHLCV, затем пишет совместимые с Freqtrade Feather-файлы.
- Локально экспортировано 521 101 свеча Binance `5m` по 10 парам. После экспорта повторно подтверждены отсутствие пропусков, дубликатов и некорректных OHLCV.
- Подготовлен отдельный конфиг без секретов `user_data/config_backtest_binance.json`. Он не заменяет серверную конфигурацию рабочего бота.
- Baseline выполнен в Freqtrade `2026.6` за период `20260125-20260723`: 1000 USDT, позиция 100 USDT, `max_open_trades = 1`, комиссия 0,1% на сторону, все 10 пар, стратегия без изменения сигналов.
- Получено 1094 сделки: 296 прибыльных и 798 убыточных, win rate 27,1%, profit factor 0,47, итог `-262,15 USDT` (`-26,22%`), финальный баланс `737,85 USDT`, максимальная просадка 26,29%. Все пары и все месяцы оказались убыточными.
- Из-за ограничения одной позиции отклонено 3720 сигналов. Отдельный тест с `max_open_trades = 3` дал 1714 сделок, но ухудшил результат до `-40,12%` и просадку до 40,22%; увеличивать лимит рабочего бота не следует.
- Контрфактический тест без комиссий всё равно дал `-4,01%` при profit factor 0,88. Следовательно, комиссии резко усиливают убыток, но положительного преимущества у текущих сигналов нет и до расходов.
- `lookahead-analysis` проверил 100 сигналов и не обнаружил утечки будущего.
- `recursive-analysis` показал, что `startup_candle_count = 50` недостаточен для полной стабильности RSI/EMA; около 200 стартовых свечей устраняют измеримое отклонение. Это кандидат на отдельное изменение следующей версии, а не основание переписывать зафиксированный baseline.
- Основной ZIP-результат, CSV lookahead-проверки и дополнительные сценарии сохранены в `user_data/backtest_results/`; крупные данные и результаты не предназначены для GitHub.

### Решения по дальнейшей архитектуре

- Текущая `TrainingStrategy` остаётся контрольным baseline и не считается готовой к реальной торговле. Ожидание новых сделок не улучшит её автоматически.
- Для регулярных бэктестов, отчётов и будущего FreqAI решено создать на VDS отдельный сервис `freqtrade-research`, а не запускать тяжёлые исследования внутри рабочего `freqtradebot`.
- Планируемый research-сервис должен читать PostgreSQL только в режиме `READ ONLY`, работать без биржевых ключей, иметь отдельный конфиг и постоянный volume для данных, моделей и результатов.
- Рабочий dry-run, сборщик данных и PostgreSQL не должны останавливаться или перезапускаться при исследовательских задачах.
- На 2026-07-25 21:00 создано Apple Reminder «Развернуть freqtrade-research на VDS».

- Добавлен воспроизводимый runner: read-only экспорт PostgreSQL → Feather, проверка временной сетки и OHLCV, baseline-бэктест, SHA-256 входных файлов и manifest запуска без секретов.
- Локальный контейнерный тест на обновлённом наборе из 521 101 свечи завершился успешно: 1104 сделки, `-26,69%`, profit factor 0,4693. Отличие от первого baseline объясняется дополнительными свечами в обновлённом локальном экспорте.

## 2026-07-23 — первый работающий контур сбора данных

### Что настроено

- Развёрнут `freqtradebot` в Easypanel на ветке `stable` репозитория `antondvinyaninov/FreqtradeBot`.
- Freqtrade работает только в режиме `dry_run`: сделки симулируются, реальные средства и API-ключи для торговли не используются.
- Биржа — BingX; отслеживаются пары `BTC/USDT`, `ETH/USDT`, `SOL/USDT`, `DOGE/USDT`; рабочий таймфрейм — `5m`.
- Включён Web UI Freqtrade.
- Создана PostgreSQL-база `bd-freqtrade`. `freqtradebot` подключён к ней через `FREQTRADE__DB_URL`; запуск подтверждён строкой `Using DB: "postgresql+psycopg://..."` в логах.
- Создано отдельное приложение Easypanel `market-data-collector`. Оно не торгует и не использует биржевые ключи: получает публичные OHLCV-свечи BingX и сохраняет их в PostgreSQL.

### Данные

- В PostgreSQL создана таблица `market_candles` с уникальным ключом по бирже, паре, таймфрейму и времени открытия свечи.
- Первый цикл записал по 1000 свечей для каждой из четырёх пар.
- Следующий 5-минутный цикл подтверждён SQL-запросом: по каждой паре стало по 1001 свече, а последняя свеча имела время открытия `23:50 UTC`.
- Сборщик запускается каждые 300 секунд и обновляет незакрытую последнюю свечу через upsert.

### Исправление

- Выявлена и исправлена ошибка пакетной вставки в PostgreSQL: `Connection.executemany` заменён на `cursor.executemany`.
- Исправление отправлено в GitHub: commit `b00b2a7fb` (`Fix PostgreSQL candle batch inserts`).

### Что это означает

- У нас есть воспроизводимый учебный контур: бот в dry-run, данные в PostgreSQL, отдельный сборщик и возможность проверять данные SQL-запросами.
- Это не подтверждает прибыльность стратегии и не является основанием для перехода к реальным сделкам.
